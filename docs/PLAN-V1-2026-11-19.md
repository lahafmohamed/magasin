# Plan v1 — nolyxERP (2026-11-19)

> Issu de l'interview « grill-me » (4 rounds, toutes branches résolues). Décisions validées par le propriétaire.
> **Aucune implémentation avant le « go ».** À l'exécution, chaque phase sera déclinée en tâches bite-sized (TDD, commits fréquents) selon la convention `plan`.

## Objectif

Une **v1 fiable, sérieuse et claire**, vendable à des boutiques de tous métiers (Afrique de l'Ouest, zone FCFA). Pas de clients existants — « Hitek » était l'instance de test. Priorité absolue : **fiabilité et image**, pas la vitesse de sortie ni la quantité de fonctionnalités.

Étoile du nord (propriétaire) : *« la sensation d'utiliser un logiciel sérieux et clair, pas un truc d'amateur »*.

## Décisions verrouillées

1. **Nom commercial : nolyxERP.** `PRODUCT_NAME` (avant connexion, titre d'onglet, démo, marketing). Après connexion, chaque client voit le nom de sa propre entreprise (`company_settings.nom`) — inchangé.
2. **Périmètre modules v1** (via le système d'exclusion existant, sans supprimer de code) :
   - **Cœur garanti** : factures, devis, bons de livraison, retours, avoirs, contacts, relances, inventaire, étiquettes, inventaire physique, caisse, vente comptoir, dépenses, audit caisse, commandes fournisseur, suggestions d'achat, réceptions, factures fournisseur, rapports, utilisateurs, journal d'audit, paramètres.
   - **Cachés en v1 (→ v2 ou option)** : paie, employés, comptabilité, trésorerie.
   - **Au choix du client** : emplacements, transferts, demandes de réappro, affectations, analyse clients, valorisation.
3. **Les 4 profils métier** (général, informatique, habillement, libre-service) sont tous validés bout en bout en v1 — le produit est multi-métiers, pas « informatique seulement ».
4. **Déploiement : décision reportée**, au choix de chaque client (hébergé / local / VPS). L'outillage VPS existant (`deploy/` : provision, update, backup, test-restore, suspend, démo) est la base. L'installateur « local Windows » est un chantier post-v1.
5. **Offline : v1 hébergée = connexion internet requise**, états d'erreur explicites (déjà designés). Pas de file d'attente/synchro offline en v1. Les sites mal connectés → mode local (plus tard).
6. **TVA : aucune en v1** (migration `027_enforce_no_tax`), limitation assumée et documentée. Cible : commerces non assujettis. Réintroduire la TVA plus tard = chantier transverse (montants, PDF, base).
7. **Champ « AI »** (paramètres société, pied des PDF) : conservé, libellé en toutes lettres (sens exact à confirmer par le propriétaire), et le PDF **n'imprime que les champs juridiques remplis** (aujourd'hui « AI : - » s'imprime dès que le NIF existe).
8. **Barre de fiabilité en 7 points** (ci-dessous) = définition de « fini ». Aucune nouvelle fonctionnalité tant qu'elle n'est pas verte.

## Phases (séquencées)

### Phase 0 — Fondations & défauts in-scope
- Renommer le produit en **nolyxERP** : `frontend/src/lib/brand.ts` (`PRODUCT_NAME`), `Login.tsx`, `index.html`, `useDocumentTitle`, démo.
- Vérifier l'état des défauts #2–#5 ci-dessus ; corriger ceux qui sont in scope (conversions devis→facture et BL→facture, seed démo).
- Champ « AI » : libellé en toutes lettres dans `CompanySettings.tsx` ; `PDFService.ts` n'imprime que les champs remplis.
- **Validation** : tests existants verts + nouveaux tests sur les conversions et le PDF ; commit par correction.

### Phase 1 — Périmètre v1 & profils
- Préréglage v1 : modules cachés par défaut sur instance neuve (paie, employés, comptabilité, trésorerie) ; presets par profil cohérents avec `profilsActivite.ts`.
- Vérifier le blocage d'accès direct par URL pour tout module masqué (`routeAccess`, `moduleForPath`).
- **Validation** : tests de masquage par profil ; parcours de chaque profil sur instance neuve.

### Phase 2 — Fiabilité argent/stock
- Suites backend + frontend complètes vertes (référence : 550 BE / 605 FE au 10 nov).
- Invariants testés : totaux identiques entre écrans (liste/détail/PDF), caisse équilibrée à la clôture, stock jamais négatif en silence, annulation contre-passée + réintégrée, allocations E1 expliquées.
- Walkthroughs personas (caissière, vendeur, magasinier dépôt, gérant, admin) **par profil métier**, sur le produit rendu avec base seedée.
- **Validation** : chaque flux cœur documenté bout en bout sans dead end, feedback après chaque action, récupération d'erreur.

### Phase 3 — Gates & passe « sérieux »
- Reconstruire le harnais de capture (base jetable seedée via `ci-db-setup.mjs`, vrai backend, Chromium headless, axe-core ; clair/sombre × 1440/1366/390/320 + vue par rôle).
- Re-passer les gates visual/copy/usability : fermer **GV-50** et **E1-R1** (déjà corrigés en code — confirmer sur le rendu), **ré-identifier CPG2-01** (rapport r2 absent du repo) et le fermer.
- Passe « sérieux » ciblée : tout ce qui lit « amateur » dans les flux cœur et sur les **documents imprimés** (facture, devis, BL, avoir, ticket 80 mm, étiquettes) — la facture imprimée est le visage du produit.
- Backlog mineur (~79) : corriger ce qui est visible dans les flux cœur, logger le reste pour v1.1.
- **Validation** : 0 violation axe serious/critical, 0 erreur API/JS à l'écran, gates signés (plus de Blocker/Major ouvert).

### Phase 4 — Démo & préparation ops
- Réparer le seed démo ; provisionner l'instance démo publique (reset nocturne vérifié, branding nolyxERP).
- Tester sur environnement de staging : `provision-client.sh`, `update-client.sh` (migration N→N+1 sans perte), `backup-all-clients.sh`, `test-restore.sh`, `suspend-client.sh`.
- Premier login = changement de mot de passe forcé (vérifié) ; runbook ops à jour dans `deploy/README.md`.
- **Validation** : cycle complet provisionner → utiliser → sauvegarder → restaurer → mettre à jour → suspendre → réactiver, sans perte de données.

### Phase 5 — Acceptation
- La checklist des 7 points est verte, preuve à l'appui (captures, rapports de tests, logs de restauration).
- Tag `v1`. **La décision de sortie appartient au propriétaire.**

## Barre de fiabilité — définition de « fini » (adoptée)

1. Défauts connus corrigés dans le périmètre v1 (conversions, annulation, seed démo).
2. Les 3 Majors des gates fermés (GV-50, CPG2-01, E1-R1).
3. Tests BE + FE verts ; invariants argent/stock testés (totaux cohérents, caisse équilibrée, stock jamais négatif en silence, flux bout en bout).
4. Chaque profil métier parcouru bout en bout par ses personas.
5. Provisionner / mettre à jour / sauvegarder / restaurer / suspendre testés ; migration sans perte.
6. Démo publique propre à reset automatique ; premier login = changement de mot de passe forcé.
7. Rien de cassé au clavier, à 390 px, en thème sombre (socle accessibilité maintenu).

## Hors périmètre v1 (explicite)

- Paie, employés, comptabilité, trésorerie (code conservé, modules cachés → v2/option).
- TVA, synchro offline, installateur local Windows, licence/activation.
- Prix, abonnement, process commercial (choix d'hébergement par client).
- Multi-tenant partagé (le modèle reste une instance par client).
- Nouvelles fonctionnalités ; refonte du logo (monogramme actuel suffisant) ; backlog mineur au-delà des flux cœur.

## Ouvert (ne bloque pas le plan)

- **Sens exact de « AI »** → libellé final à confirmer par le propriétaire avant la phase 0.
- **Contenu exact de CPG2-01** → ré-identification au gate copy (phase 3).
- Nettoyage des données de test historiques (202 annulations, 41 écarts) ou reseed complet — cosmétique, aucun client réel.
- Assets de marque nolyxERP (logo/monogramme, domaine de démo).
- Chantier commercial post-v1 : hébergement au choix du client, installateur local, licence, prix.
